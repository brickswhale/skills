# route

The references hold the rules; this orders them. It writes a registry, a policy and one briefing line.

1. **Read** `references/registry-format.md` (format, states, checks, updating), `references/policy-template.md` (the policy, its Contract and Roles), `references/lines.md`, and `pair`'s `references/transports.md` (call shapes).
2. **Classify**, and open with `ROUTE — setup` or `ROUTE — update`. The registry sits beside the `pair` record; the policy is where the project briefing points. No registry: setup. A registry: update. No policy here: write one from the template.
3. **Enumerate**: read the tools' own lists and config; run only the version and list commands of tools `pair`'s catalog recognises, and for any other tool check only that it exists. Ask the owner for what no file shows: subscriptions, each kept model's tier, what may go where, exclusions. List what the owner reserves; the choice stays theirs.
4. **Draft, check, show.** Draft every change together, run the registry reference's checks on the drafts, and show them with each transport's family, its read-only story and every failed check. Write on the owner's yes: one wrong registry misroutes every project on the machine. An explicit instruction to make a change is that yes for the change it names. Draft inside the directories you are changing.
5. **Report what is stale** in the `pair` record and in a policy's own obligations and Retired lines; those texts stay as written.
6. **Report** files written; profiles added, changed or gone; every rank a change touches, per project; failed checks; the choices waiting for the owner.
