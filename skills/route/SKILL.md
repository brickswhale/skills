# route

The references hold the rules; this orders them.

1. **Read** `references/registry-format.md`, `references/policy-template.md`, `references/lines.md`, and `pair`'s `references/transports.md`.
2. **Classify**: no registry beside the `pair` record means setup. Print `ROUTE — setup` or `ROUTE — update` on its own line before any draft. In each project the briefing points to, write the policy from the template if it has none; if it has one, bring its Routing, Contract and Roles sections to the template's current text, since those are the template's, and keep everything else.
3. **Enumerate**: read the tools' own lists and config where the owner says the machine's config and tools live, and only there; run only the version and list commands of tools `pair`'s catalog recognises, and for any other tool check only that it exists. Ask the owner, together, for the facts no file shows: subscriptions, each kept model's tier, what counts as money or security work, what may go where.
4. **Propose, check, show.** Draft every change as one proposed policy: each preference the owner has not given becomes your recommendation marked `(proposed)`, never settled. Run the registry reference's checks on the drafts; show them with each transport's family, its read-only story and every failed check. Ask the owner to accept the proposal or change lines; ask separately only what decides who builds or reviews money or security work. Write on the owner's yes. An explicit instruction to make a change is that yes for the change it names; a go-ahead to write accepts no `(proposed)` line. Keep every temporary file, extracted templates and comparison inputs included, inside a directory you are changing, or compare in memory.
5. **Report what is stale** in the `pair` record, and what in a policy's own obligations or Retired lines is stale or contradicts the template; change those only on the owner's explicit word.
6. **Report** files written; profiles added, changed or gone; every rank a change touches, per project; failed checks; which jobs can run now and which wait, and on what. A result with a waiting job is saved, not ready: never report the checks as passed while one waits.
